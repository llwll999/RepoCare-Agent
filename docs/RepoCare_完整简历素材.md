## 1. 项目定位：一句话怎么说

**RepoCare Agent 是一个面向本地代码缺陷排查与受控修复的三角色 Agent Demo：用户用自然语言提交 Bug，系统先检索代码与本地知识库形成证据，再生成最小 diff，在隔离 Sandbox 中回归验证；只有人工二次确认后才允许写入真实源码。**

它不是“让大模型直接改文件”的聊天工具，而是将 **诊断、提案、验证、审批、落地、可追溯记录** 串成受约束流程的 Agent 工程。

### 业务演示场景

- **分值导出重复**：旧版本记录已被替代，但导出时仍可能累计其分值；系统定位 `superseded` 字段缺失过滤，并提出最小修复 diff。
- **班级综合测评小程序重复提交**：同一学生、同一材料类别、同一网页条目被重复提交时，系统定位云函数中的材料创建逻辑，提出“查询已有 pending / approved 材料后拒绝重复写入”的修复方案。

第二个场景来自真实业务规则，但 RepoCare 对它只做**本地 Sandbox 验证和人工确认后的受控落地**；没有把生产数据或密钥上传至 GitHub。

## 3. 实际架构：你需要讲清楚的全链路

```text
自然语言 Bug / 演示场景
        │
        ▼
FastAPI + Web UI（创建 Run、查看进度、反馈、批准）
        │
        ▼
原生 Python Orchestrator（DemoRun + 有限状态机）
        │
        ├── 调试 Agent：只读代码搜索 + Local RAG 证据 + 可选 DeepSeek 结构化诊断
        ├── 修改 Agent：按白名单规则生成最小 diff，不直接写真实文件
        └── 测试 Agent：临时 Sandbox 中运行回归测试，独立给出报告
        │
        ├── SQLite：任务 / 检查点 / 运行快照 / 已验证经验 / 知识索引
        ├── MCP：search_repo_code、search_local_knowledge 两个只读工具
        └── 交付门禁：人工批准 → 校验源文件哈希 → 备份 → 写入 → 回归测试 → 失败回滚
```

### 状态流转

```text
INTAKE → INVESTIGATING → PLANNING → WAITING_FOR_APPROVAL
                                              │
                                              ▼
PATCHING → VERIFYING → RESOLVED
                 │
                 ├──────────────→ INVESTIGATING（验证失败，重新取证）
                 └──────────────→ NEEDS_HUMAN（证据不足、规则已存在或风险超范围）
```

这张图的价值在于：**LLM 不是流程的唯一裁判**。状态白名单、审批门禁与测试结果共同决定任务是否能往下走。

## 5. RAG：当前真正实现了什么

### 当前实现（可以写进简历）

1. 只从 `knowledge_base/` 读取脱敏 Markdown，跳过 `.git`、`.venv`、`node_modules`、缓存目录；避免将整个项目、日志或密钥无差别喂给模型。
2. 依据 Markdown 标题切分章节，再按段落和长度切块；单块最大约 720 字符，保留约 100 字符重叠，减少信息被截断。
3. 为每个块保存 `source_path / heading / content / content_hash`，写入本地 SQLite 索引，保证结果能够回指来源。
4. 第一版使用离线中英文稀疏文本特征（中文字符 n-gram + 英文词）和余弦相似度计算相关度，不需要下载 Embedding 模型，也不会产生向量 API 费用。
5. 返回 Top-K 证据中的路径、标题、片段与分数，并在界面中展示；模型收到的是明确标注为“只读参考、不可视为写入授权”的证据。

### 不应该夸大成什么

- 不是 FAISS / Chroma 向量数据库。
- 不是神经网络 Embedding 语义检索。
- 没有使用 LangChain 的 Loader、TextSplitter 或 Retriever。
- 不能说“已经解决所有幻觉”；项目通过证据展示、白名单和测试降低风险，而不是消灭风险。

### 面试中 30 秒解释 RAG

> 我没有把整个代码仓或所有历史对话直接塞给模型，而是限定知识库目录，按标题和段落切块，给每块保留来源和哈希。Bug 到来后先用离线稀疏检索取回最相关的 Top-K 规则和排障文档，再把它们作为只读证据交给调试 Agent。这样上下文更小、答案可以回溯，也避免知识库内容被当成写入授权。

## 6. Agent、工具、记忆与验证：为什么不是普通聊天机器人

### 三 Agent 是怎样分工的

| 角色 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 调试 Agent | 搜索允许范围内的源码、检索 RAG、形成根因和证据 | 不直接改文件、不替代测试结论 |
| 修改 Agent | 根据已取证规则提出最小 diff | 不自行扩大修改范围、不绕过批准 |
| 测试 Agent | 在 Sandbox 运行回归测试，产出通过/失败报告 | 不因为“模型认为对”就判定成功 |

当前是**受控的顺序工作流**，并不假装成多个模型并发自治协作。这样的实现更适合面试解释：先把每个角色的输入、输出、权限和停止条件写清楚，再考虑并行化。

### 为什么要把 Memory 与 RAG 分开

- **短期记忆 / Checkpoint**：当前 Run 的状态、聊天记录、补丁、测试报告；用于服务重启后继续处理当前任务。
- **长期记忆**：只写入“已验证成功”的模式，并按场景限制召回数量；不会把用户原始问题、密钥或未经证实的猜测长期保存。
- **RAG 知识库**：稳定的业务规则、架构说明和排障 Runbook；每次检索都有来源，不等于任务历史。

这三个东西解决的问题不同：RAG 解决“我需要查什么知识”，短期记忆解决“这次任务走到哪一步”，长期记忆解决“验证过的经验能否复用”。

## 7. 安全与工程化亮点

1. **最小权限**：MCP 暴露的是只读搜索工具；写文件不是通用 Tool，而是在固定业务场景和审批流程内受控执行。
2. **路径白名单**：代码搜索限制根目录和查询格式，防止 `../` 路径越界。
3. **幂等**：Patch Ledger 使用请求键避免同一个写入请求被重复处理。
4. **人工在环**：修改 Agent 的输出先是 diff；测试通过后仍要输入二次确认文本才允许真正落地。
5. **落地前一致性校验**：比较源文件 SHA-256，源文件在审核期间变了就拒绝覆盖。
6. **可恢复性**：保存任务 Checkpoint 与运行快照，写入前备份；回归失败自动回滚。
7. **保守失败策略**：若检测到目标源码已有防护规则，或证据不足，进入 `NEEDS_HUMAN`，而不是为了展示“修复成功”硬生成重复补丁。

## 10. 高频面试题：简洁且真实的回答

### Q1：你的项目用了 LangChain 吗？

**没有直接使用。** 当前版本的状态机、切块、检索、模型协议、工具和审批都是原生 Python 实现的。我这样做是为了先把输入输出、权限、证据来源和测试边界做透明。后续如果文档源变多、需要切换不同的 Embedding 或向量数据库，我会评估用 LangChain 的 Loader / Text Splitter / Retriever 抽象替换 RAG 层；但状态机、审批和 Sandbox 不会交给框架黑箱处理。

### Q2：为什么不用“模型自己判断已经修好”？

模型只能给出假设，不能替代结果。RepoCare 要求补丁在隔离目录执行回归测试，测试 Agent 的报告才是进入下一步的依据；而真实写入还需要人工批准。

### Q3：你的 RAG 和记忆有什么不同？

RAG 是从稳定知识文档中按需检索证据；短期记忆保存这次任务进度；长期记忆只保存已通过验证、可以复用的经验。混在一起会让上下文膨胀，也会把未经证实的内容当作事实。

### Q4：为什么多 Agent 不并发？

当前任务的依赖关系是“先取证、再提案、再验证”，盲目并发会造成对同一文件提出冲突 diff，也增加成本。先采用顺序角色流；当工具调用相互独立时，例如多个只读检索，才值得并行。

### Q5：怎样防止模型把错误内容写进项目？

模型没有直接通用写权限。它只能生成结构化诊断或受控 diff；路径、审批、哈希、备份、Sandbox 测试和回滚都在模型外部执行。无法满足前置条件时进入 `NEEDS_HUMAN`。

## 11. LangChain / LangGraph：目前与未来的正确写法

| 技术 | 当前状态 | 简历能否写“已使用” |
| --- | --- | --- |
| 原生 Python Agent 工作流 | 已实现 | 可以 |
| Local RAG（稀疏检索 + SQLite） | 已实现 | 可以 |
| MCP 工具服务器 | 已实现 | 可以 |
| DeepSeek API 结构化诊断 | 已实现，但为可选能力 | 可以写“接入可选模型诊断”，不要写模型全自动修复 |
| LangChain | 未安装、未 import | 不可以 |
| LangGraph | 未安装、未使用 | 不可以 |
| Embedding + FAISS / Chroma | 未实现 | 不可以 |

如果之后要真正加入 LangChain，最合理的改动是替换 RAG 的“加载 / 切块 / Retriever”层，并补齐对应测试；如果要使用 LangGraph，则把当前的状态与审批暂停/恢复显式映射成图节点。完成真实集成和回归测试后，才能将其写入简历。
